# 重彩游戏技术方案

**迁移进度。** Go 已提供 WebSocket、房间目录、实时同步和 PostgreSQL 自动存档。权威玩法规则与浏览器复用 TypeScript 源码，由服务进程内的 V8 执行。旧服 JSON 可通过导入命令迁入 PostgreSQL。单机与联机旅行者已共用 Go 模型接口。管理后台已提供房间准入、持久世界备份和旅行者调用链调试。生产构建已生成带完整性摘要的单机资源清单，浏览器通过 Service Worker 缓存资源并支持停服后从本机存档重开。目标是发布一份浏览器前端和一个 Go 游戏服务，由 Go 同端口提供游戏、管理页面、HTTP API 和 WebSocket。PostgreSQL 保存联机与管理数据。下文描述迁移后的行为及上线前的验收条件。

## 1. 运行模式与部署

| 使用场景 | 哪一端推进游戏 | 存档与服务依赖 |
| --- | --- | --- |
| 单机 | 浏览器生成世界、推进 NPC、处理玩家操作 | 角色和世界存在本机浏览器。首次在线缓存完成后，关闭 Go 和 PostgreSQL 也能重新打开游戏、读档并继续保存 |
| 联机 | Go 维护每个房间的世界时钟、共享进度和玩家个人状态，浏览器负责输入、渲染、预测与插值 | Go 将世界与玩家一起存入 PostgreSQL。玩家切换模式时分别打开对应存档 |
| 管理 | 服主从同站的 `/admin` 访问当前 Go 实例 | 房间运行数据来自 Go，管理员、会话、审计和备份来自 PostgreSQL |

  UI --> Local["浏览器存储 · 单机存档和离线资源"]

**部署。** 游戏发布物包含 Go 可执行文件和一份静态资源目录。可复用已有 PostgreSQL 实例，或单独部署数据库。只有 Go 读取 `DATABASE_URL` 并通过连接池访问数据库。Go 可在对外端口提供 TLS。后续新增账号、运营或 NPC 管理时，在同一 Go 模块中扩展业务包，并在现有前端增加页面。

**前端构建。** 保留 TypeScript、Three.js 和现有美术资源。Go 构建命令调用 esbuild 的 Go API，锁定并校验依赖，接管路径别名、资源基址、HTML 入口和城市生成 Worker 的独立打包。管理路由按需加载。迁移期间需验证独立原生 TypeScript 检查器能执行项目的严格类型检查，并将 Vitest 用例按职责迁至 Go 或浏览器。以干净环境仅用 Go 工具和浏览器完成构建、检查与测试，作为移除 Node.js 工具链的验收条件。[esbuild Go API](https://esbuild.github.io/api/) · [TypeScript 转译与类型检查](https://esbuild.github.io/content-types/#typescript)

## 2. 服务入口与职责

Go 使用 `net/http` 提供静态文件和 HTTP 路由，使用 `github.com/coder/websocket` 处理 WebSocket。房间目录、世界模拟、存档、旅行者 AI 和管理 API 均为进程内模块。[WebSocket 库说明](https://github.com/coder/websocket)

| 同源入口 | 行为 |
| --- | --- |
| `/`、静态资源 | 返回游戏入口、离线资源清单与前端发布物 |
| `/multiplayer` | 升级 WebSocket，订阅房间列表，创建、加入和重连房间，交换玩家输入、世界补丁和快照 |
| `/admin`、`/api/admin/v1/*` | 加载管理界面，通过管理 API 登录、查看运行情况、调整准入或备份。API 校验管理员会话后调用房间与存档模块 |
| `POST /api/traveller-plan` | 在线单机可请求旅行者选站。联机房间直接调用相同的 Go 模块 |

## 3. 离线单机

1. **首次在线打开。** 菜单自动开始下载并显示进度。构建时生成包含版本、大小和内容摘要的清单，覆盖入口 HTML、脚本、样式、动态模块、城市 Worker、模型、纹理、界面和声音，包括尚未进入过的场景。离线字体使用系统字体。
2. **确认可以离线。** Service Worker 将清单内的同源资源写入 Cache Storage。资源全部通过校验、离线导航已生效、本机存档可持久写入，菜单才显示「已可离线游玩」。中断后联网补齐缺项，空间不足或只能写入内存时显示原因及重试入口。
3. **关闭浏览器后重开。** 在同一设备和浏览器配置中打开原网址，Service Worker 返回完整缓存版本。玩家可继续最近的本机世界、用带 `?world=` 的书签进入指定世界，或选择其他存档、新建世界。存档沿用现有 `localStorage` 键和迁移逻辑。地形生成、NPC 活动、旅行者见闻和自动保存在浏览器执行，服务可用性探测在后台进行。
4. **更新资源。** 新版本下载到独立缓存，全部校验后在下次启动切换。已有标签页继续使用原版本，关闭后才清理对应的旧资源缓存。更新中断时沿用完整旧版，存档保存在独立的浏览器存储中。

部署应保持协议、主机和端口稳定，线上使用 HTTPS，本机开发可用 localhost。离线重开以浏览器保留站点数据为前提。离线导航只处理游戏入口与清单资源，管理页面、API 和 WebSocket 走网络。打开房间邀请遇到停服时，提示「联机服务暂不可用」，由玩家选择是否打开本机世界。[Service Worker 使用说明](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers) · [浏览器存储配额与回收](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

## 4. 联机房间与状态同步

**进入房间。** 玩家点「联机」后通过同源 WebSocket 查看房间名称、人数及上限、密码保护和准入状态，游戏 URL 无需附加服务器地址。开放房间点选即加入，密码房提示输入，也可创建房间。以现有 JSON 协议 v9、6 位房间号和玩家身份令牌为兼容基线。保留握手超时、来源校验、消息大小和频率限制、心跳，以及版本不兼容和拒绝加入时的原因提示。

**房间生命周期。** Go 在进程内管理一个持久世界和多个临时房间。每个房间串行处理玩家输入、时钟、管理员命令和 AI 结果。加入操作和准入变更在同一循环内判定。持久世界可在重启后恢复。临时房间在最后一人离开 5 分钟后回收，服务重启时结束。回收时在同一事务删除临时世界及其玩家记录，启动后先清理遗留临时世界再开放创建。房间号可复用，存档按稳定世界 ID 关联，管理操作按房间实例标识定位。

**同步与重连。** Go 约以 20 Hz 发送邻近玩家快照，包含世界时钟和当前分配的看守客户端。保留玩家位置上报、看守客户端推进指定城镇事件、服务端竞技场战斗判定，以及共享补丁的序号、确认、纠正与广播。慢连接可合并过时的位置快照，补丁和纠正按序交付；无法继续交付时允许断开重连。重连使用原身份令牌取得最新世界快照和本人的进度。替换旧连接后，迟到的断开事件仅清理对应旧会话。

## 5. PostgreSQL 存档与恢复

| 记录 | 标识与内容 |
| --- | --- |
| 联机世界 `world_saves` | 以稳定世界 ID 为主键，记录世界类型、格式版本、保存序号和 JSONB 共享状态。包括世界种子、地形版本、时钟、城镇修复进度及旅行者行程和见闻 |
| 联机玩家 `player_saves` | 以世界 ID 和玩家身份键为联合主键。身份键由原令牌计算稳定摘要。记录名称、外观、个人进度（含库存）及上次出现的世界时间 |
| 世界备份 | 按唯一操作编号记录来源世界、保存序号、格式版本、校验摘要和完整快照，涵盖该世界所有已保存玩家 |
| 管理数据 | 管理员、会话和操作记录。管理会话与玩家令牌分别校验。随 Go 发布版本化 SQL 迁移 |

**一次保存的边界。** 定时自动保存、玩家离开和正常停服时，房间提取同一时刻的世界状态与玩家集合，交给后台任务写入。实时位置广播与数据库保存分别调度。每个世界按序提交，一个事务同时更新世界及玩家进度，提交成功后才标记已保存。重连活跃房间时使用内存中的最新状态，持久世界在进程重启后从最后一次完整提交恢复。

**数据库中断。** Go 继续提供静态页面，联机和管理入口提示服务暂不可用。如果活跃房间保存失败，暂停受影响房间的推进，提示进度待保存，保留待写快照并重试。连接恢复后先核对已提交序号，补交最新快照再继续游戏。若 Go 在重试期间退出，持久世界只能恢复到最后一次成功提交。

**备份与恢复。** 备份取同一时刻的完整世界和玩家集合，重复操作编号返回原结果。恢复前暂停世界、排空待写任务并校验备份。在同一事务内替换共享状态和全部玩家记录，使用新的保存序号，提交后重新加载房间并让客户端同步。世界备份与运行数据位于同一数据库，数据库实例故障后的恢复依赖独立的实例备份。

## 6. 旅行者与管理后台

**旅行者行为。** 世界模拟负责生成沿路可达的候选站点，并记录旅行者到访过的地点、当时村况和见闻时间。玩家询问来处、去向、附近村况或过去经历时，游戏按行程和世界记录回答。在线选站时，Go 将候选地点、距离、行进方向和最近见闻发送给模型，要求返回形如 `{"stop": 0}` 的候选序号。Go 校验整数范围，联机房间还需核对房间实例、行程版本和站点可达性，再采纳并广播结果。模型调用在房间循环外执行。离线、未配置模型、超时或输出无效时，旅行者按已有行程和本地规则继续活动。

模型接口兼容 Chat Completions。服务端读取 `INKBLOOM_AI_BASE_URL`、`INKBLOOM_AI_MODEL` 和按供应商需要配置的 `INKBLOOM_AI_API_KEY`。管理界面与审计摘要只展示诊断所需信息，密钥、房间密码和玩家身份令牌均由服务端保护。

| 管理页面 | 可查看 | 首版操作 |
| --- | --- | --- |
| 总览 | 采样时间、运行时长、在线连接、活跃房间、最近保存结果 | 进入对应房间、世界或操作记录 |
| 房间与世界 | 人数及上限、密码保护、准入状态、回收倒计时、种子、时钟、存档版本和备份 | 暂停或恢复临时房间加入，备份指定持久世界 |
| 旅行者与 AI | 行程、村庄见闻，以及接入监测后的候选站点、选站、耗时和回退原因 | 按世界、旅行者和时间查询 |

管理页面默认每 5 秒读取最近快照，失联时显示数据已过期。管理写操作校验会话、CSRF 令牌和目标实例，以操作编号审计。调整准入后，已在房内的玩家继续游戏，房间列表同步更新，新的加入和重连按当前规则处理。协议通过版本或能力字段引入新增状态。

## 7. 迁移与切换

| 阶段 | 交付与通过条件 |
| --- | --- |
| 固定兼容基线 | 留存脱敏协议样本、旧存档和固定种子样例。对照 Go 与浏览器在负坐标、随机数、整数运算、地表指纹、道路、村庄 ID、资源位置、旅行者轨迹上的结果 |
| 迁移联机与数据库 | 将 WebSocket、房间目录、模拟、补丁、快照、竞技场和 AI 适配迁入同一 Go 服务，接入 PostgreSQL。回放协议并验证双客户端同步、断线重连和跨房隔离 |
| 整合前端与离线入口 | 同一构建产出游戏、管理路由、Service Worker 和版本化资源清单，验证无 Node.js 构建、类型检查及离线冷启动 |
| 演练与正式切换 | 先以旧档副本演练导入、备份、恢复和回退。切换时停止旧服新房准入、通知并排空临时房，冻结写入并保存最终旧档，导入校验后由 Go 接管原入口 |

旧档导入识别 `world-data/<世界>.json` 外层 v1、现有加载器支持的内层版本（当前为 v10）和各玩家切片。每个世界在一个事务内导入。记录源文件摘要和目标世界 ID，相同输入重复导入返回原结果，已有进度与导入来源冲突时报告冲突。导入后比对种子、时钟、旅行者见闻和玩家数量，并用原令牌核对库存。保留旧发布物和只读源文件。若新服已产生玩家进度，回退前先验证旧服能读取待保留的进度。

## 8. 发布验收

| 场景 | 操作与通过标准 |
| --- | --- |
| 首次缓存与离线冷启动 | 全新浏览器配置在线打开，看到「已可离线游玩」后保存位置与库存。退出浏览器、停止 Go 并断开测试数据库，设备保持联网，从原网址重开并核对存档；再断网从世界书签冷启动 |
| 离线探索与再次保存 | 进入此前未到过的村庄，验证城市 Worker、角色模型和音频。修改进度，退出重开后核对改动。分别中断首次缓存和版本更新，验证前者可补齐，后者可沿用完整旧版并保留存档 |
| 双人联机与管理 | 在单个 Go 实例和同一个对外地址测试开放房、密码房、满房和准入变更。两名玩家核对共享进度，第三个浏览器执行管理操作。验证跨房隔离、好友拜访、手势、竞技场判定、补丁拒绝纠正与旅行者记忆同步 |
| 存档归属与临时房回收 | 两名玩家取得不同库存，保存后重启 Go，用各自原令牌回到持久世界，核对共享进度与个人库存。临时房回收后复用同一房间号，确认新世界及玩家进度独立 |
| 事务中断与备份恢复 | 在世界与玩家写入之间制造失败，核对上一份完整存档。恢复连接并重试，验证旧序号无法覆盖新进度。备份后改变世界并加入一名玩家，再恢复，核对玩家集合与世界同时回到备份时刻，重启后审计记录和备份仍可查询 |
| 旅行者降级 | 使模型超时、返回越界序号或在行程已变更后返回。验证房间继续推进，旅行者沿有效路线行动，对话能引用已保存的见闻 |
